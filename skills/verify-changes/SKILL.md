# 変更を確かめる

入力は変更差分、受入条件、利用可能な環境、既存の検証証拠。

1. Projectの手順と変更範囲から、必要なformat/lint/typecheck/test/build/実操作を選ぶ。すべてを毎回走らせない。
2. 検証の選択や失敗の扱いを判断する時に[検証ガイド](../../context/verification.md)を読む。参照はこのSkillの実体ディレクトリ(symlink先)から解決する。
3. コマンドが対象環境で安全に実行できることを確認し、実行結果と終了コードを読む。失敗を黙って無視したり成功文字列だけでpassとしない。
4. 今回の変更が原因の失敗は修正して影響するcheckを再実行する。原因不明ならsystematic-debuggingで調べる。同じ差分に十分な証拠があれば再実行しない。

出力は対象状態(HEADとdirty差分)、check、結果、未検証範囲の短い表。UIやiOSの実動作を、静的検査だけで検証済みとしない。

完了条件は、受入条件とcheckが対応し、pass/失敗/未実施が区別されていること。設計や変更漏れの評価はself-reviewへ渡す。検証手段の不足を理由にsandboxを解除したり外部作用を追加したりしない。
